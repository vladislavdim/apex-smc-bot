# Аудит APEX — 30 сентября 2026

Ошибки подтверждены. Главный эксплуатационный дефект: успешное восстановление зеркала базы закрывало инцидент, но оставляло `state_db=FAILED`. Из-за этого живой бот мог часами не принимать новые сделки. Исправления в этом изменении направлены на восстановление, работу SQLite, Telegram и входные данные индикаторов. Это не доказательство отсутствия любых ошибок или прибыльности стратегий.

## Исправленные дефекты

| Приоритет | Дефект и влияние | Исправление / проверка |
|---|---|---|
| P1 | Cutover закрывал инцидент, но оставлял FAILED у базы и блокировал новые сделки | Независимые причины отказа компонента. Восстановление снимает только свой отказ; другая ошибка зеркала, ошибка схемы и незавершённый запуск сохраняют блокировку. Регрессионное воспроизведение fail → recover → admission |
| P1 | `evaluate_readiness()` игнорировал `required=False`; таймаут периодического backup блокировал торговлю вопреки политике задачи | Единая оценка обязательности компонента. Периодический backup остаётся видимым DEGRADED, но не выключает исправную торговую цепочку. Начальный State-checkpoint и `STATE_BACKUP_DEFERRED` сохраняют защиту |
| P1 | Необязательное обновление исторических зон объявлялось отказом основного `market_data` и останавливало новые входы | Отдельный компонент `market_intelligence`, необязательная фоновая задача. Проверки свежести Gate и обязательного торгового входа остаются действующими |
| P1 | Поиск обработанного события зоны выполнял полный scan таблицы из 108 378 событий; при исключении соединение могло остаться открытым | Индекс `(zone_id,event_key)`, короткая транзакция с `BEGIN IMMEDIATE`, сериализация записей зон, rollback и гарантированное закрытие. Такой же безопасный контекст закрытия для совместимого DB writer. Тест ошибки внутри транзакции подтверждает освобождение блокировки |
| P2 | Переданный SQLite timeout заменялся на 30 секунд; повторная установка WAL дублировала политику соединения | Timeout соблюдается централизованно; лишние PRAGMA в совместимых обёртках убраны. Значение по умолчанию остаётся 30 секунд |
| P2 | Telegram доставлял уже завершившийся эпизод отдельными OPENED/RESOLVED | Единое сообщение «Сбой уже устранён» с началом, окончанием и длительностью; активные ERROR/CRITICAL остаются видимыми. Выборка не разрывает один эпизод границей батча, подтверждение доставки группы атомарно |
| P2 | Пропуск задачи с результатом `False` объявлялся успешным восстановлением | SKIPPED не снимает действующий отказ и не рисует READY без выполнения |
| P2 | Адаптивные индикаторы использовали незакрытую свечу | Вход ограничен подтверждёнными свечами. Тест с огромным изменением текущей открытой свечи не меняет результат |
| P2 | EMA200 вычислялась из запроса на 100 свечей и отсутствовала при реальном расчёте | Запрашивается 201 свеча: 200 закрытых плюс открытый хвост. Проверка использует настоящую EMA-функцию, а не заглушку |
| P2 | В режиме snapshot уже закрытая последняя свеча отбрасывалась повторно | Общий фильтр учитывает `is_closed`; применён также в SMC-анализе. Для старых неразмеченных данных сохранён drop-last |

Для SQLite добавлены безопасные диагностические поля `sqlite_errorcode` / `sqlite_errorname`, без SQL и содержимого базы. Они позволят отличить BUSY/LOCKED от ошибок схемы и I/O при следующем эпизоде.

На копии реальной brain.db 100 поисков отсутствующего события: **0,6243 с → 0,0005 с**. План изменился с `SCAN historical_zone_events` на `SEARCH ... USING COVERING INDEX`. Это измерение локального запроса, а не обещание такого же ускорения всего сканера на Render.

Совпадение ошибок зеркала с часовым обновлением зон и отсутствие индекса делают конкуренцию за SQLite правдоподобной причиной. Она остаётся гипотезой относительно конкретных старых `OperationalError`: исходных сообщений исключений нет. Возможность долгих транзакций и утечки соединения подтверждена кодом и тестом.

## Стратегии, риск, LONG/SHORT

По журналу scan_runs с 29.09: FAST — 440 проверок пар, MTF — 1707, SWING — 2520, ZONE — 2533, WYCKOFF — 620. Для этих запусков `data_failed=0`. Это подтверждает выполнение сканирования, но не гарантирует достаточную историю для каждой внутренней проверки; предыдущая ошибка короткого кэша устранена в PR #179.

Основные отказы: `LOW_LIQUIDITY`, `NO_STRATEGY_SETUP`, `REGIME_DISABLED`, `WAIT_LTF_CONFIRMATION`. Эти причины сами по себе не являются багами. Два доставленных ZONE-сигнала прошли отдельный LTF watcher. Не следует ослаблять риск или фильтры только ради появления ордеров.

Проверки покрывают направление SL/TP, минимальный RR, свежесть входа, ограничения риска и плеча, дневной стоп, доступный баланс, биржевые фильтры, повторную отправку, частичное исполнение, восстановление intent и сохранение защиты до подтверждения Binance.

Для SHORT выполнен дополнительный полностью изолированный сценарий: одобренный BEARISH → положительный sizing → запрос SELL с `positionSide=BOTH` → подтверждённый заглушкой fill → стоп выше entry и два TP ниже → закрывающие BUY → сохранённый статус PROTECTED. Проверены также отклонение hedge mode до отправки, направление переноса short-стопа и обработка TP/SL менеджером существующими тестами. Реальная сеть/ордера для проверки не использовались.

Поддерживается **One-way mode**. Hedge mode явно возвращает `SKIPPED_HEDGE_MODE`; наличие SHORT не означает поддержку одновременных независимых LONG/SHORT по одной паре.

В доступной State-базе **0 execution_fills** и всего 4 записи исполнения — все BULLISH и со статусами отказа. Поэтому реальные исполненные шорты этими данными **не подтверждены**. Также нет базы для оценки фактической прибыльности какой-либо стратегии.

Диагностика новых отказов уже расширена PR #179. Увеличение риска автоматически до биржевого минимума не добавлялось.

## Что ещё требует улучшения

1. **Разгрузить State и резервирование.** 189,7 MB из 236,5 MB занимают только `setup_audit_events`, без индексов: 131 021 строк за девять дней, все синхронизированы. Успешный backup в среднем занимает 216 с, максимум 298 с при лимите 300 с; 5 запусков вышли за лимит. Перенести подробную телеметрию в отдельное хранилище, оставить в State торговую истину и компактные ссылки. Разделить критический State backup и тяжёлые Memory/brain backup по расписанию. Существующая история автоматически не удалялась.
2. **Уточнить математический контракт индикаторов.** В legacy adaptive-классе `adx` — одно значение DX без сглаживания ADX; `atr` — средний high−low без учёта разрыва к предыдущему close, `atr_med` — среднее, а не медиана. Это подтверждённое несоответствие названий и формул. В данном исправлении сохранены существующие формулы и пороги: замена на Wilder ADX/ATR меняет стратегические решения. Следующий шаг — отдельная версия индикаторов, числовые эталоны и сравнение кандидатов на сохранённых рыночных данных до включения новой версии.
3. **Расширить рыночные примеры.** Закреплённый corpus содержит только пять случаев, по одному на стратегию. Нужны принятые и отклонённые LONG/SHORT для нескольких пар и режимов рынка, включая гэпы, низкую ликвидность, границы свечей и переходы сессий. Текущий parity — проверка совместимости, не доказательство доходности.
4. **Сделать торговую цепочку видимой.** Для каждого signal_id показывать единый путь: найден → одобрен → риск → размер → отправлен → filled → защищён → закрыт. Аналитический сигнал не должен выглядеть как открытая позиция Binance. При минимальном размере показывать рассчитанные quantity/notional и действующие фильтры.
5. **Уменьшить влияние медленных внешних сервисов.** Сохранить ограниченные очереди и отдельные бюджеты времени для цен, контекста и backup; контролировать p95 длительности и размер баз. После отмены `asyncio.to_thread` синхронная работа может продолжаться. Для backup уже есть внутренний thread-lock; для зон он добавлен здесь. Нужна дальнейшая проверка фоновых запросов и graceful shutdown под нагрузкой.
6. **Проверять восстановление отдельно от отправки сообщения.** Метрика должна показывать не только закрытие конкретного инцидента, но и фактические `ready/new_entries/reason_codes`. Уже устранённый отказ компонента не означает, что сняты остальные независимые блокировки.

## Проверка изменения

Локально: полный pytest, unittest, production authority/release-ready gates, пять закреплённых parity cases, проверка diff; дополнительно регрессионные сценарии восстановления, необязательных задач, SQLite rollback/index, уведомлений, EMA200 и закрытой свечи. Точный итог CI и развернутый SHA фиксируются в PR и controlled production release. Торговые ордера в ходе аудита не отправлялись.

После выпуска требуется наблюдение реальных периодических циклов: старт и READY проверяются отдельно от следующего часового обновления зон и следующего backup. Краткая проверка после деплоя не доказывает, что все будущие таймауты исчезнут.

Техническая основа управления транзакциями: [SQLite transaction documentation](https://www.sqlite.org/lang_transaction.html). SQLite допускает одного writer; короткие транзакции и обязательное закрытие важнее увеличения таймаута.
