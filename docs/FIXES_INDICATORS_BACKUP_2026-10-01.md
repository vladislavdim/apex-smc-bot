# APEX: исправления индикаторов, резервного копирования и диагностики

Подготовлено 30 сентября — 1 октября 2026 года. База сравнения: production
`8a123b2a4bd04227af4b8deeea5f92739150ac81` (PR #180, релиз #31).

## Индикаторы и стратегии

- Общая функция ATR теперь учитывает предыдущую цену закрытия и сглаживание
  Wilder. Дубли вычисления среднего `high-low` удалены из FAST, MTF, SWING,
  ZONE, анализа накопления, оценки момента входа и контекста рынка.
- ADX использует сглаженные направленные движения, начальное среднее DX и
  последующее сглаживание Wilder. Минимальная история ADX14 — 28 свечей.
  На плоском рынке ADX равен нулю, а не выдуманным 20. При отсутствии данных
  адаптивная проекция возвращает `adx=null`, `indicators_ready=false`.
- `atr_med` — медиана последних 50 True Range, а не среднее диапазонов.
- EMA в определении рыночного режима рассчитывается общей функцией EMA;
  незакрытые свечи исключаются. Средний предыдущий объём использует 20 свечей.
- Контракт индикаторов помечен `wilder-v1`. Пороги RR, риска, ликвидности,
  размера позиции и ограничения Binance не ослаблены.

Численные эталоны сгенерированы независимой TA-Lib 0.6.8, которая нужна только
при подготовке эталона, а не при запуске бота. В репозитории сохранены входные
свечи и ожидаемые результаты. Проверено 60 значений ATR/ADX: рост, падение,
плоский рынок, разворот, разрыв цены и колебания; пять длин истории для каждого
сценария. Допуск сравнения — 1e-10.

Источники математического контракта:
- https://ta-lib.org/functions/atr.html
- https://ta-lib.org/functions/adx.html

Сравнение полного старого и нового кода на пяти закреплённых рыночных
сценариях: решения, причины остановки и геометрия не изменились. У ZONE
изменился численный операнд ATR в журнале: 885.65 → 1006.9555791291432.
Проверка миграционного соответствия интерфейсов также проходит с исходным
закреплённым verdict `a292e2d92852`. Это ограниченная регрессия, не доказательство
прибыльности или неизменности всех будущих сигналов.

## Резервное копирование и размер State

Ранее одна задача последовательно обслуживала State, Memory и brain в общем
лимите 300 секунд. Теперь задачи имеют отдельные лимиты и расписание UTC:

| Хранилище | Минуты часа |
| --- | --- |
| State | 03, 33 |
| Memory | 13, 43 |
| brain | 23, 53 |
| Audit | 09, 19, 29, 39, 49, 59 |

Тяжёлые снимки защищены общей блокировкой процесса. Если после отмены async
задачи поток ещё работает, следующий снимок пропускается, а не накапливает
ожидающие потоки. Пропуск не выдаётся за успешное восстановление.

Новые диагностические события направляются в `apex_audit.db` после её
проверенного восстановления или безопасной инициализации. Резервная копия
`apex_audit.db` хранится в существующей ветке `apex-memory-backups`, независимо
от файла Memory. Если подготовка Audit не удалась, используется прежний State
outbox; торговый процесс не должен падать из-за необязательной базы.

Старые события переносятся порциями по 10 000. Порядок: скопировать → сверить
содержимое → успешно сохранить Audit в GitHub → удалить совпадающие исходные
диагностические строки из State. При ошибке, конфликте или занятом копировании
исходные строки сохраняются. Торговые таблицы не удаляются. Повтор после
рестарта безопасен и идемпотентен. Архивирование занимает несколько циклов;
освободившиеся страницы State переиспользуются. Сжатие/уплотнение выполняется
над временным снимком, без `VACUUM` рабочей торговой базы.

Проверка на локальной копии рабочего State, 248 512 512 байт:
- 10 000 событий скопированы за 0.567 с, удалены после имитации подтверждённого
  сохранения за 0.475 с; 126 620 исходных событий остались на следующие циклы.
- Audit: 15 360 000 байт; gzip: 2 165 683 байта, сжатие 0.093 с.
- Проверка SQLite `quick_check`: OK. Эти измерения локальные, не время GitHub
  или Render; реальные production данные в ходе теста не изменялись.

Memory теперь тоже сжимается; уровень gzip 1 снижает процессорную нагрузку.
Лог резервного копирования содержит хранилище, результат, длительность,
исходный/передаваемый размер и число архивированных событий.

## Дополнительные найденные дефекты

- Проверка изменений копии ошибочно пропускала любое SQL-представление строки,
  содержащее слово `heartbeat`. Теперь исключаются только конкретные служебные
  таблицы; изменение реального текста со словом heartbeat учитывается.
- Большой JSON обрезался посреди синтаксиса. Теперь сохраняется валидный
  ограниченный объект с идентификаторами, признаком усечения и предпросмотром.
- Размер HTTP-пакета диагностических событий ограничивается байтами с учётом
  экранирования Unicode, а не количеством символов/событий.
- Соединения диагностического outbox закрываются и при исключениях.
- Controlled release скачивает историю только main, сохраняя проверку
  принадлежности коммита main; ветки с тяжёлыми резервными копиями не нужны.

## История конкретного сигнала

Добавлена команда только для чтения локальных скачанных снимков:

```sh
python scripts/inspect_signal.py 465 --state /path/apex_state.db \
  --memory /path/apex_memory.db --brain /path/brain.db
```

Она связывает числовой signal_id с каноническим signal_entity_id и показывает
кандидата, Groq/risk данные, lifecycle, исполнение, ордера, fills и действия
менеджера. Недоступные источники явно обозначаются. Наличие аналитического
сигнала или order_id не считается подтверждением исполнения: нужны fills.
Проверено на сигнале 465: записи State, Memory и brain найдены, fills отсутствуют.

## Проверки и ограничения

Покрыты численные эталоны, симметрия LONG/SHORT, разрывы, недостаточная история,
невалидные OHLC, устойчивость медианы, архивирование при отказе и изменении
исходной записи, повторное архивирование, сохранность торговых таблиц,
конкурирующие резервные копии, Unicode-пакеты, связность истории сигнала.

State-снимок после релиза #31 содержит job_runs до 30.09.2026 14:05 UTC:
после старта 12:29:19 UTC в нём нет новых инцидентов и завершённых ошибкой задач.
Это не устанавливает причину каждого более раннего OperationalError.
Новые длительные наблюдения и живые исполнения SHORT следует оценивать по
реальным данным; тестовые торговые ордера не отправлялись.

Локальные итоговые проверки: 954 pytest, 814 unittest, compileall,
release-ready, production authority и исходный закреплённый parity verdict.
Проверка production перед выпуском 01.10.2026 около 10:33 Europe/Warsaw:
`READY`, входы ON, но `backup` и `memory_db` DEGRADED; процесс по-прежнему
запущен 30.09.2026 12:29:19 UTC. Поэтому сообщения о сбое резервного копирования
не доказывают перезапуск процесса. Новый код разделяет статус резервной копии
Memory и работоспособность самой Memory DB, включая стартовый checkpoint.

## Дополнительная проверка production 01.10.2026

Релиз #32 (run 36837805952) завершился failure в 08:53:53 UTC:
код a812fc65 уже запустился, но readiness не прошёл. В журнале подтверждён
GitHub create_blob HTTP 422: input was too large. Это не конфликт CAS.
В 14:01 UTC worker продолжал работать с started_at 08:43:57 UTC;
backup был READY, но STATE_BACKUP_DEFERRED всё ещё запрещал новые входы.
Ограниченная серия startup-повторов исчерпалась, а плановый успешный backup
не снимал этот запрет.

Исправление: каждый подтверждённый saved/unchanged State checkpoint снимает
только STATE_BACKUP_DEFERRED и закрывает соответствующий incident.
Ошибки, busy, stale_remote и not_configured не снимают защиту; другие причины
запрета сохраняются. Ошибка размера больше не обозначается concurrent_update
и не вызывает пять одинаковых Contents-запросов. При gzip >32 MiB используется
повторное сжатие level 6 вместо level 1 с ограниченным потреблением памяти.

Production-перенос истории подтверждён: State snapshot g410 от 14:03:19 UTC
содержит 0 setup_audit_events и занимает 21 950 464 bytes. Независимая Audit
snapshot g28 от 13:59:39 UTC содержит 157 011 событий. Это реальные резервные
копии, а не локальный benchmark. История сохранена отдельно.

Локальная проверка дополнения: 957 pytest passed (15.55 s), в том числе
снятие только нужного запрета, сохранение запрета при неуспехе,
классификация oversized 422 и обратимость плотного gzip.
